# Phase 35 Durable Outbound Webhook Worker

Status: kickoff planning and source coverage only; no dispatcher, queue, retry loop, signing runtime, admin retry control, or live outbound webhook delivery is enabled.

Last updated: 2026-06-05

## Scope

Phase 35 turns stored webhook configuration and event-log foundations into durable outbound delivery foundations for configured integrations.

This kickoff slice defines the safety boundary, record lifecycle, retry planning surface, signing expectations, and source-guard expectations before any runtime dispatcher is introduced.

## Goals

- Define a provider-neutral outbound webhook delivery contract for configured integrations.
- Preserve existing webhook configuration readiness without sending outbound requests.
- Plan durable delivery-attempt lifecycle states before any queue or dispatcher exists.
- Define retry/backoff and terminal failure expectations before enabling automated retries.
- Define payload signing expectations without introducing signing runtime or secret access in this slice.
- Keep admin retry/cancel controls deferred until durable state and authorization boundaries exist.
- Add source coverage so future slices cannot silently add live delivery behavior to the kickoff foundation.

## Safety boundaries

Do not add or enable these behaviors during the Phase 35 kickoff slices:

- Outbound HTTP delivery to configured webhook targets.
- Queue consumers, scheduled jobs, background loops, or automatic dispatchers.
- Retry/backoff execution.
- Payload signing runtime or direct secret reads.
- Admin retry, cancel, replay, or force-send controls.
- Dead-letter mutation flows.
- Concrete production endpoint defaults beyond existing placeholder/readiness examples.
- Production-ready claims for outbound webhook delivery.

## Relationship to existing foundations

Existing webhook configuration foundations already provide:

- Stored webhook configuration shape.
- Target URL normalization and readiness checks.
- Subscribed event names.
- Header-name and signing-secret environment-variable naming.
- Admin settings surface for configuration readiness.

Phase 35 should build on those foundations without treating stored configuration as operational delivery until dispatcher, persistence, signing, retry, and admin recovery surfaces are explicitly guarded.

## Planned delivery record shape

A future outbound webhook delivery record should describe a single event delivery attempt or logical delivery job.

| Field | Purpose | Notes |
| --- | --- | --- |
| `id` | Stable delivery record identifier. | Generated by application or database. |
| `configurationKey` | Webhook configuration used for delivery. | References stored webhook settings. |
| `eventType` | Event name, such as `order.created`. | Must match configured subscription terms. |
| `eventRef` | Safe reference to the business event. | Prefer internal ids over raw payloads. |
| `payloadDigest` | Stable digest of the outbound payload. | Supports idempotency and audit without storing full body. |
| `idempotencyKey` | Prevents duplicate logical delivery. | Required before retries. |
| `status` | Provider-neutral lifecycle state. | See lifecycle states below. |
| `attemptCount` | Number of attempted outbound sends. | Must remain zero until dispatcher exists. |
| `lastOutcomeCategory` | Safe outcome summary. | Accepted, non-2xx, timeout, unavailable, cancelled, or failed. |
| `nextEligibleAttemptAt` | Future retry eligibility timestamp. | Planning only until retry execution exists. |
| `lastResponseCode` | Safe HTTP status summary, if available. | Do not store sensitive response bodies. |
| `createdAt` | Creation timestamp. | Required. |
| `updatedAt` | Last update timestamp. | Required. |

## Planned lifecycle states

The future lifecycle should remain integration-neutral and safe for admin visibility.

- `planned`: delivery was planned but no outbound request was made.
- `queued`: eligible for future dispatcher execution.
- `sending`: reserved for active dispatcher execution.
- `accepted`: target returned a successful response category.
- `non_2xx`: target returned a non-success response category.
- `timeout`: delivery attempt timed out.
- `unavailable`: target or network appeared unavailable.
- `retry_wait`: delivery is waiting for retry eligibility.
- `cancelled`: operator or policy cancelled delivery before completion.
- `dead_letter`: delivery reached terminal failure policy.
- `failed`: delivery failed without further retry eligibility.

## Retry and backoff planning

Before retry execution is implemented, define these expectations:

1. Maximum attempt count.
2. Initial delay and backoff multiplier.
3. Jitter policy.
4. Which outcome categories are retryable.
5. Which outcome categories are terminal.
6. How retries preserve idempotency.
7. How dead-letter records become visible to admins.

No retry execution belongs in this kickoff slice.

## Signing expectations

Payload signing should be added only after the delivery record and dispatcher boundaries exist.

Future signing work should define:

- Canonical payload string or byte representation.
- Timestamp header expectations.
- Signature header names.
- Secret source name handling without storing secret values.
- Verification examples for operators.
- Rotation behavior.

This kickoff slice should not read signing secrets or compute runtime signatures.

## Admin visibility expectations

Admin visibility should come after the durable delivery record exists.

Future admin surfaces may show:

- Delivery status.
- Safe event references.
- Attempt count.
- Last safe outcome category.
- Next eligible retry timestamp.
- Terminal failure/dead-letter summary.

Admin retry/cancel controls should remain deferred until authorization, confirmation UX, idempotency, and audit logging are explicitly covered.
