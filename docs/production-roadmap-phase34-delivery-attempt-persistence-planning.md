# Phase 34 Delivery-Attempt Persistence Planning

Status: documentation-only persistence planning; no database migration, retry worker, admin retry control, or live provider delivery is enabled.

Last updated: 2026-06-05

## Purpose

This document defines the repo-side planning shape for future notification delivery-attempt persistence before any schema migration, retry worker, or live provider send path is introduced.

Phase 34 should establish the persistence contract and safety gates. Phase 35 owns durable outbound worker behavior.

## Safety boundary

- Do not add or apply database migrations in this slice.
- Do not add live email, SMS, or WhatsApp provider calls.
- Do not add retry workers, queues, cron jobs, or background send loops.
- Do not add admin send or retry controls.
- Do not store confidential provider configuration values, customer personal data beyond the minimum required identifiers, or raw provider payloads.
- Keep `liveDeliveryEnabled` false until operator evidence and a separate live-enablement change exist.

## Planned delivery-attempt record

A future persisted delivery-attempt record should describe one planned or attempted notification delivery without embedding confidential provider material.

| Field | Purpose | Notes |
| --- | --- | --- |
| `id` | Stable delivery-attempt identifier. | Generated by the application or database. |
| `channel` | Email, SMS, WhatsApp, or future channel. | Must match provider-neutral contract terms. |
| `scenario` | Business notification scenario. | Examples: order confirmation, staff notification, inquiry acknowledgement, fulfillment update. |
| `recipientKind` | Customer, staff, operator, or integration target. | Avoid storing unnecessary recipient details. |
| `recipientRef` | Internal reference to recipient target. | Prefer internal ids or safe references over raw personal data. |
| `providerMode` | Disabled, manual, log, or provider-backed. | Mirrors readiness diagnostics and delivery contract planning states. |
| `providerName` | Operator-selected provider name if known. | Optional until provider-backed mode is approved. |
| `templateKey` | Application template identifier. | Do not persist provider dashboard content or secret material. |
| `idempotencyKey` | Prevents duplicate sends for the same logical notification. | Required before any retry behavior. |
| `status` | Planned lifecycle state. | See lifecycle states below. |
| `attemptCount` | Number of actual provider attempts. | Must remain zero for no-send/manual planning records. |
| `lastOutcomeCategory` | Safe outcome summary. | Accepted, rejected, rate-limited, unavailable, suppressed, skipped, or failed. |
| `nextEligibleAttemptAt` | Future retry eligibility timestamp. | Planning only until Phase 35 worker exists. |
| `lastProviderReference` | Safe provider correlation reference, if available. | Never store confidential provider payloads. |
| `createdAt` | Record creation timestamp. | Required. |
| `updatedAt` | Last record update timestamp. | Required. |

## Planned lifecycle states

The future persisted status field should remain provider-neutral and safe to expose in operations views.

- `planned`: delivery payload was planned but not sent.
- `skipped`: delivery was intentionally skipped because delivery is disabled or suppressed.
- `manual_required`: operator action is required outside automated delivery.
- `logged`: delivery was recorded through log/manual mode with no provider send.
- `queued`: eligible for a future worker after Phase 35 introduces durable worker behavior.
- `sending`: reserved for future worker execution.
- `accepted`: provider accepted the delivery request.
- `rejected`: provider rejected the delivery request.
- `rate_limited`: provider or policy delayed delivery.
- `unavailable`: provider was unavailable or staging harness simulated unavailability.
- `failed`: terminal failure after approved retry policy is exhausted.
- `suppressed`: consent, opt-out, or suppression policy blocked delivery.

## Idempotency expectations

Before any live or retry behavior exists, every planned delivery should define a deterministic idempotency key shape.

Recommended key components:

1. Channel.
2. Scenario.
3. Business object type and id, such as order or inquiry.
4. Recipient kind and safe recipient reference.
5. Template key or template version.
6. Environment name when needed to avoid cross-environment collisions.

Idempotency must prevent duplicate sends for the same logical notification while still allowing a later intentional replacement message when business state changes.

## Retention and privacy expectations

- Store only the minimum metadata needed for operations, support, and auditability.
- Avoid raw message bodies where possible; store template keys and safe render metadata instead.
- Avoid raw provider payloads; store safe outcome categories and correlation references only.
- Define retention windows before live delivery.
- Define redaction behavior for customer deletion or privacy requests before live delivery.

## Relationship to Phase 35

Phase 35 should build on this planning document when introducing durable outbound worker behavior.

Phase 35 must still separately define:

- Queue ownership and locking semantics.
- Retry backoff and maximum attempt policy.
- Dead-letter or terminal failure handling.
- Worker observability.
- Admin recovery surfaces.
- Source guards preventing accidental live provider execution.

## Open implementation questions

- Which database model owns notification attempts: a shared notification table or channel-specific tables?
- Which business objects need first-class links: order, inquiry, fulfillment, payment, refund, or staff alert?
- Which recipient references are safe enough for audit while minimizing personal data retention?
- Which outcome categories should be shown to admins versus kept operator-only?
- What retention windows satisfy support needs without over-retaining delivery metadata?

## Completion criteria for this planning slice

This planning slice is complete when:

1. The future record shape is documented.
2. Lifecycle states are documented without enabling a worker.
3. Idempotency expectations are documented.
4. Privacy and retention expectations are documented.
5. The Phase 34 tracker points to the next inert adapter slice.

This slice must not include schema changes, queue behavior, live provider calls, retry controls, or production-ready delivery claims.
